## 1. Драйверы архитектуры

| Драйвер | Источник | Что требует от архитектуры |
|---|---|---|
| ≤ 2 мс MSPT на 10 000 растений | Видение, GDD §13 | Никаких тикающих BlockEntity у растений, никакого сканирования мира. Опыление считается по событию, геном компактен |
| Сервер авторитарен, выделенный сервер | Видение п. 5, метрика 5 | Движок и логика работают только на сервере. Общий код не трогает `net.minecraft.client`. Все пакеты от клиента проверяются |
| Данные, а не код: новый вид только через JSON | Видение, метрика 6 | Виды и сорта приходят из датапака. Должен существовать путь, на котором растение работает без своего Java-класса и без своего блока |
| ≤ 6 вариантов стака на предмет | Владелец п. 19 | Урожай несёт в NBT только класс и горечь. Геном лежит только в посадочном материале |
| Старые сохранения грузятся | Задание фазы 2 | Каждый сохраняемый корень несёт версию. Миграции покрыты тестами. Неизвестные данные не удаляются |
| Выпуск волнами, линия = модуль | Владелец п. 15, GDD §20 | Линию включает набор данных. Код от волны к волне почти не меняется |
| Ошибка в JSON не роняет сервер | Видение, GDD §14 | Мягкая загрузка: плохая запись пропускается, а в лог уходит путь и причина |
| FD — soft-dependency, но поддержка обязательна | Владелец п. 4, 8 | FD-код изолирован в одном пакете. На каждый хрупкий хук есть запасной путь без FD-классов |
| Минимум mixin | Задание | Сначала Forge-события, AT и подклассы ванильных классов. Mixin только там, где без него никак, и каждый случай записан в ADR |
| Детерминизм | GDD §3.8, §9.5, worldgen §3.3 | Свои RNG и хэши с зафиксированным алгоритмом. Никакого `java.util.Random` и `String.hashCode` в генетике |

**Атрибуты качества по приоритету:** корректность сохранений, затем производительность сервера, сопровождаемость (команда маленькая, Minecraft зафиксирован на 1.20.1), расширяемость данными и только потом гибкость кода.

**Поток данных при посадке лота:** `SeedLotItem.useOn` (сервер) → `PlantService.plant(level, pos, lot, player)` → `GeneticsService.realizeOffspring(lotRecord, rngKey)` → `Genome` → `GeneticsService.phenotype(genome, species, env, noise)` → `PlantBlockEntity` хранит геном, шум и паспорт, а блок получает `BlockState` со стадией, размером и вариантом. Клиент видит только `BlockState`.

**Направление зависимостей:** `client → mod → genetics`. `compat.* → mod`. Никто не зависит от `compat`: связь с FD, JEI и Jade идёт через Forge-события и аннотации плагинов, которые сторонние моды находят сами. `genetics` не знает о Minecraft.

## 4. Генетический движок

Решение: ADR-0001. Движок — подпроект `:genetics` без `net.minecraft` на classpath. Чистоту гарантирует компилятор: импорт Minecraft просто не соберётся.

### 4.1 Порт между движком и Minecraft-слоем

Minecraft-слой сам переводит JSON в записи движка, собирает среду клетки и хранит результат. Движок получает только простые значения.

```java
public interface GeneticsService {
  GenomeLayout layout(SpeciesDef species);                         // кэшируется по species
  Genome wildPlant(SpeciesDef s, PatchPassport p, long plantKey);  // ленивый дикий геном (worldgen §3.3)
  Genome villagePlant(SpeciesDef s, VillageTemplate t, long key);  // шаблон деревни (GDD §9.5)
  Genome offspring(LotRecord lot, long rngKey);                    // мейоз матери × мейоз выбранного отца + мутации
  Genome clone(Genome g);                                          // копия без мейоза
  NoiseVector rollNoise(SpeciesDef s, long rngKey);                // ε при посадке (GDD §3.1)
  Phenotype phenotype(Genome g, SpeciesDef s, Environment e, NoiseVector n);
  Classification classify(Genome g, SpeciesDef s, List<CultivarDef> profiles, Optional<CultivarId> parentStatus);
  List<FatherPick> chooseFathers(SpeciesDef s, Genome mother, List<Candidate> nearby, List<Donor> donors, long rngKey);
  int grade(Phenotype p, CultivarDef cultivar);                    // класс 1–4 (GDD §6.4)
  ProcessingResult process(List<GradedInput> mains, List<Booster> boosters); // GDD §6.6
  GenomeRecord encode(Genome g);  Genome decode(GenomeRecord r, SpeciesDef s); // §5
}
```

`Environment` — запись `(temperature, moisturized, light, compostBonus)`. Её считает `ClimateService` в мод-слое из клетки: температура с поправкой на высоту — одна функция для роста и для worldgen (GDD §3.2). `Candidate` — `(Genome, dx, dy, dz, sAlleles)`. Движок не знает, откуда взялся кандидат (индекс цветения, пчела, кисть).

### 4.2 Состав движка (покрывает GDD §3–§6)

| Функция | Модель | Стоимость |
|---|---|---|
| Генотипическое значение | `G = Σ аллелей / (4·L)` по локусам признака | O(L) |
| Компромиссы, слой 1 | `G_pair(A) = max(0, G(A) − Σ c·max(0, G(B) − θ))`, штраф от исходного `G(B)`, циклы разрешены | O(пар) |
| Компромиссы, слой 2 | Бюджет `S = Σ wᵢ·G_pair(i)`; если `S > limit`, то масштаб `limit/S` | O(признаков) |
| Витальность | `V = step^(число dd)` по 8 локусам груза | O(8) |
| Фенотип | `P = clamp(G_eff·V + E + ε, 0, 1)`, `V` только для признаков с `vigor_affected` | O(признаков) |
| Мейоз | Свободная рекомбинация: независимый выбор аллеля на локус, мутации с вероятностями вида (шаг ±1 с обрезкой для количественных, переключение для качественных) | O(локусов) |
| Классификация | Наибольшая ступень, затем `priority`; гистерезис `−hysteresis` для потомков сорта; у клона статус сохраняется; `hysteresis: 0` у яблони отключает наследование статуса | O(признаков × профилей) |
| Выбор отцов | Reservoir sampling до 64 кандидатов, до 4 отцов с весом `1/(1+d²)`, плюс до 4 доноров; самонесовместимость «общий S-аллель = отказ» | O(64) |
| Дикая популяция | Элитные локусы из `Hash64(worldSeed, species, category)`, аллели по частотам фон/элита, начальный `wild_F` | O(локусов) |
| Качество | `Q = Σ w·P` по `quality_axes` сорта → класс по границам 0.35/0.55/0.75; горький урожай не выше 2 | O(осей) |
| Переработка | `g_raw = floor(среднее взвешенное)`, потолок по ступени (1/3/4), бустер +1 (≤ cap+1, ≤ 4) | O(входов) |

Пороги, частоты и коэффициенты движок в коде не держит: всё приходит из `SpeciesDef`/`CultivarDef`. Значения по умолчанию (например, `limit` 2.6) живут в одном классе `Defaults` и подставляются при загрузке JSON с предупреждением в лог (GDD §14).

### 4.3 Детерминизм (ADR-0001)

- **RNG:** свой `SplitMix64`, состояние `long`. Алгоритм зафиксирован тестом с эталонными значениями. `java.util.Random` (его `nextGaussian` в JDK 17 меняли) и `SplittableRandom` не используются.
- **Хэши:** `Hash64.of(long...)` — смешивание SplitMix-финализатором. Строки (id вида, признака) хэшируются через FNV-1a 64 по UTF-8 и никогда через `String.hashCode`.
- **Гаусс:** свой Box–Muller на `SplitMix64`.
- **Ключи RNG** (вычисляет мод-слой, использует движок):

| Событие | Ключ |
|---|---|
| Потомок при посадке | `Hash64(secret, lotId, remainingCount, packedPos)` — уточнение GDD §3.8 (§21, п. 1) |
| ε при посадке | `Hash64(secret, lotId, remainingCount, packedPos, "noise")` |
| Дикое растение | `Hash64(worldSeed, patchOrigin, plantPos)` (worldgen §3.3) |
| Деревенское растение | `Hash64(worldSeed, villagePos, landraceId, harvestCount)` (GDD §9.5) |
| Выбор отцов при завязывании | `Hash64(secret, plantUid, cycleIndex)` |
| Реализация ленивого лота (трава, сундук, торговля) | `Hash64(secret, lotId)`. `lotId` назначается **при создании предмета**, в том числе ленивого (`tpl.lotId`), а не при реализации (SEC-13). Поэтому половины стака, разделённого до реализации, получают одинаковые `lotId` и геном, а разделение стака `lotId` никогда не меняет |

- **Секрет мира** (SEC-25): `SavedData` `wildroots_secret` — `long` из `SecureRandom`, создаётся при первой загрузке overworld. Он никогда не уходит клиенту, не пишется в лог и не выводится командами, а класс `WorldSecret` недоступен из `network`, `client` и `compat` (правило ArchUnit). Движок получает секрет как обычный `long`-аргумент ключа и о его происхождении не знает. Внутри мира детерминизм сохраняется (перезаход ничего не перебрасывает), но модифицированный клиент, знающий геном лота и алгоритм движка, не может вычислить конкретного потомка для клетки и знает только распределение (`09-security.md` §1.8, T-I2). Ключи worldgen и деревень остаются на `worldSeed`: мир должен воспроизводиться по сиду.
- **`lotId`** — 64 бита из `SecureRandom` или `Hash64(secret, gameTime, counter)`.

- Java 17 считает `double` строго по IEEE (JEP 306), поэтому вычисления с плавающей точкой воспроизводимы на любой JVM.

### 4.4 Валидация определений (в движке, поэтому тестируется JUnit)

`DefinitionValidator.validate(SpeciesDef)` возвращает `List<Problem>`, а не бросает исключение. Что проверяется: число локусов 1–16 на признак; частоты аллелей в сумме 1 ± 1e-6; `tradeoffs` и `budget` ссылаются только на объявленные признаки; `c ≥ 0`; `θ` и пороги лежат в `[0, 1]`; число элитных локусов не больше числа локусов; у S-локуса 2–16 аллелей; у сорта требования ссылаются на существующие признаки и аллели; сумма `quality_axes` равна 1 (иначе нормализация и предупреждение). Ошибка уровня `ERROR` отбрасывает запись, `WARN` применяет значение по умолчанию.

Числовые границы всех полей определений (число видов и сортов, признаков, пар `tradeoffs`, диапазоны `c`, `limit`, мутаций, радиуса опыления 0–16, времени стадий, `food_reference`, итог раскладки ≤ 512 бит) задаёт таблица `DataLimits` из `09-security.md` §1.6.6 (SEC-28). Все числа обязаны быть конечными: `NaN` и `±Infinity` дают ERROR. Граф ссылок (сорт → вид, шаблон → ландрас, роль → тег) разрешается одним проходом с поиском циклов, глубина ≤ 16 (SEC-29). Функции движка тотальны на валидированных входах: деления на 0 нет, результаты проходят `clamp`, циклы ограничены лимитами (SEC-30).

## 5. Геном: представление, NBT, версии, миграция

Решение: ADR-0002.

### 5.1 Раскладка локусов (`GenomeLayout`)

Раскладка выводится из `SpeciesDef` детерминированно: секции идут в каноническом порядке `quantitative` (по id признака), затем `load`, затем `qualitative` (по id). Внутри секции — локусы по номеру, на каждый локус два аллеля (материнский и отцовский).

| Тип локуса | Значения аллеля | Бит на аллель |
|---|---|---|
| Количественный | 0, 1, 2 | 2 |
| Груз (`load`) | `D` / `d` | 1 |
| Качественный двухаллельный | дикий / одомашненный | 1 |
| Многоаллельный (S-локус, до 16 аллелей) | номер аллеля | `ceil(log2 n)` (10 аллелей → 4) |

Биты упаковываются подряд в `long[]`. Пример, морковь (GDD §3.9): 29 количественных локусов × 2 × 2 = 116 бит, груз 8 × 2 × 1 = 16, качественные 5 × 2 × 1 = 10, всего 142 бита, то есть `long[3]` (24 байта). Капуста с пятью видовыми признаками, S-локусом и прочим укладывается в ≈ 240 бит (`long[4]`). Потолок GDD §3.1 (~300 бит, `long[5]`) соблюдён с запасом.

`layoutHash` — 64 бита: FNV-1a 64 от канонической строки раскладки (`q:flavor:4|q:fruit_size:6|…|l:8|c:bitterness:1:2|…`; у качественного признака в строку входит число аллелей). Словарь раскладок индексируется парой `(вид, lh)` и хранит каноническую строку. Если `lh` совпал, а строка другая, определение вида отклоняется с ошибкой загрузки. Причина: коллизия FNV-1a 32 находится перебором за 284 041 правдоподобную раскладку (< 1 с), и при совпадении миграция молча декодировала бы аллели чужой раскладкой (S10, `docs/spikes/S10-genome-migration-pouch.md`). Цена — +4 байта на геном.

### 5.2 Формат NBT генома

Ключи короткие: их тысячи в чанке.

```
"g": {               // CompoundTag
  "v":  1,           // версия формата кодека (код)
  "sp": "wildroots:wild_carrot",
  "lh": -1234567890123L,  // LongTag: 64-битный layoutHash раскладки, которой закодированы аллели
  "a":  [L; ...]     // LongArrayTag, упакованные аллели
}
```

Шум растения `ε` — не часть генома. Он лежит в BlockEntity как `"e": [B; ...]`: один байт на признак, `ε` квантуется шагом 1/256 в диапазоне ±0.5.

**Лимиты при декодировании** (SEC-09, SEC-10; полная таблица — `09-security.md` §1.6.2): длина `a` должна быть **ровно** `layout.longCount`, при этом `layout.longCount ≤ 8` (≤ 512 бит); `sp` — валидный `ResourceLocation` ≤ 128 символов; `1 ≤ v ≤ CURRENT`. Декодер типобезопасен (`contains(key, TAG_*)`), не бросает исключений и возвращает `Valid | Inert(reason)`. Размер корня проверяется итеративным `NbtBudget` **до** разбора.

### 5.3 Два уровня версий и миграции

| Что меняется | Пример | Механизм |
|---|---|---|
| **Формат кода** (структура NBT) | v1 → v2: добавили поле | `"v"` в каждом сохраняемом корне. Цепочка `Migrator(vN → vN+1)` в коде, загрузка принимает любую `v ≤ текущей`, запись всегда в текущем формате |
| **Данные вида** (раскладка) | В JSON моркови у `yield` стало 8 локусов вместо 6 | `"lh"` не совпал с текущей раскладкой. Старая раскладка берётся из словаря раскладок, аллели декодируются по ней и перекодируются в текущую по ключу `(признак, локус, аллель)`. Новые локусы заполняются по фоновым частотам вида из `Hash64(genomeKey, traitId, locus, allele)`. Удалённые признаки или локусы отбрасываются с предупреждением в лог. Сужение числа аллелей и смена типа признака заменяют значения вне нового диапазона фоном с предупреждением — это единственная допустимая потеря. Мигрируются все геномы корня, в том числе отцы лота и записи мешочка (S10: 290 из 290 геномов через save/load BE, 0 потерянных аллелей; 100 000 случайных миграций в JUnit) |

**Словарь раскладок** хранится в двух местах:
1. **В jar** лежит история раскладок всех выпущенных встроенных видов (`data/wildroots/genome_layouts/<вид>.json`). Её дополняет релизная проверка CI: изменилась раскладка встроенного вида → нужна запись в истории, иначе сборка красная.
2. **В мире** лежит `SavedData` `wildroots_layouts` (overworld): `(вид, layoutHash) → каноническая строка` всех раскладок, которые этот мир видел, включая датапачные виды. Растёт только при изменении JSON, это байты.

Если раскладки нет ни там, ни там (предмет перенесён из чужого мира с изменённым датапаком), неизвестные секции генерируются заново как дикие по ключу из хэша генома, а в лог уходит предупреждение. Данные не теряются молча, и краша нет.

**Защитные правила (для всех корней: геном, BlockEntity, лот, мешочек, capability журнала, SavedData):**
- `v` из будущего (сохранение от новой версии мода открыли старой) → запись **не трогается**: сырой NBT сохраняется как есть, объект инертен (растение не растёт, лот не сажается), в лог уходит предупреждение. Даунгрейд не уничтожает данные.
- Вид или сорт отсутствует в определениях (датапак убран, линия выключена) → то же самое: сырой NBT сохраняется, растение «спит», тултип «неизвестный вид». Возврат датапака всё восстанавливает.
- Id реестров после выпуска не переименовываются. Если это всё же понадобится — `MissingMappingsEvent` с ремапом.

### 5.4 Обязательный тест-сценарий «старое сохранение грузится»

1. **JUnit (`:genetics`)**: `GenomeMigrator` на эталонных `GenomeRecord` всех выпущенных версий формата и раскладок (`src/test/resources/golden/v<N>/*.json`). Проверяется побитовое равенство ожидаемому результату. Плюс свойство «encode → decode = тождество» на 10 000 случайных геномов каждого вида.
2. **JUnit (`:mod`, без запуска игры)**: SNBT-фикстуры лота, мешочка, BlockEntity и журнала каждой выпущенной версии проходят через NBT-кодек мода и сравниваются с эталоном. Классы `net.minecraft.nbt` (`TagParser`, `NbtIo`) работают в `:mod:test` без `Bootstrap` (S10). `ItemStack`, `FriendlyByteBuf.writeItem` и `BlockEntity` требуют реестров, поэтому их сценарии идут в GameTest (п. 3).
3. **GameTest «old_save_vN»**: на каждом релизе замораживается структурный шаблон (`data/wildroots/structures/gametest/old_save_v<N>.nbt`) с растениями всех архетипов, плодами, деревом и сундуком с лотами, мешочком и клонами. Тест ставит шаблон, ждёт загрузки BlockEntity и проверяет: геномы декодируются, растения растут, лот сажается, мешочек отдаёт записи в порядке LIFO. Шаблоны прошлых релизов никогда не удаляются из репозитория.

## 6. Где живёт состояние: BlockEntity, предметы, стаки

Решения: ADR-0003 (BlockEntity), ADR-0007 (NBT предметов и стаки).

**Лимиты и инертность.** Каждый корень из таблицы имеет жёсткий лимит из `NbtLimits` (`09-security.md` §1.6.2; лот ≤ 1 КиБ (цель ≤ 512 Б), мешочек ≤ 16 КиБ и ≤ 32 записи, маточник, клон или привой ≤ 512 Б, `PlantBlockEntity`/`FruitBlockEntity` ≤ 2 КиБ с шумом ≤ 48 байт, журнал ≤ 64 КиБ). Это **дефолт до подтверждения владельцем**. Если лимит превышен или данные повреждены, объект становится **инертным**: лот не сажается и не принимается машинами, мешочком и торговлей, растение не растёт и не опыляет, а тултип пишет «повреждённые данные». Сырой тег при этом не удаляется, но и **не копируется** в новые объекты. То же относится к сырому NBT «из будущего» и неизвестного вида (§5.3).

### 6.2 Нагрузка BlockEntity на чанк

| Величина | Типичное растение | Худшее (цветёт, ожидает лот с 8 донорами) |
|---|---|---|
| Память объекта BE (заголовок, поля, `CapabilityProvider`) | ≈ 80 байт | ≈ 80 байт |
| Геном (`long[3–4]`) + шум (`byte[≈12]`) + паспорт + UUID + кэш `P` | ≈ 180 байт | ≈ 180 байт |
| Ожидающий лот (≤ 8 геномов по ≈ 40 байт + веса) | 0 | ≈ 400 байт |
| **Итого в памяти** | **≈ 0.26 КБ** | **≈ 0.7 КБ** |
| NBT при сохранении чанка (до сжатия) | ≈ 150 байт | ≈ 500 байт |

- **10 000 растений:** 2.6–7 МБ heap, 1.5–5 МБ NBT при полном сохранении (сжатый регион меньше в разы: короткие ключи повторяются).
- **Тикающих BE у растений нет** (`getTicker` → `null`). Стоимость простоя — ноль за тик. BE участвует только в случайных тиках блока, во взаимодействии и в сохранении чанка.
- **Сохранение:** чанк сериализуется, только если помечен грязным. Растение вызывает `setChanged()` только при реальном изменении (смена стадии, завязывание, сбор), как ванильная культура. Сериализация одной BE ≈ 2–5 мкс → 10 000 растений ≈ 20–50 мс на полное автосохранение, растянутое по ванильному циклу сохранения чанков. Это сопоставимо с сундуками.
- **Плотная теплица** (≈ 1000 растений в чанке): ≈ 0.7 МБ heap, ≈ 0.5 МБ NBT на чанк. Предел NBT чанка (~2 МБ на запись в регионе до внешнего `.mcc`) не достигается. `[ПРОВЕРИТЬ]` порог 1.20.1.
- **Пакет чанка клиенту:** `getUpdateTag` у встроенных видов пуст, у датапачных — только id вида (для цвета). На растение 4–30 байт.

**Альтернатива — capability чанка или `SavedData` на чанк** с картой `pos → PlantData`. Экономит ≈ 80 байт на растение, но ломает инварианты, которые BE даёт даром: удаление вместе с блоком при любом `setBlock`, перенос в шаблонах структур (процессор деревни пишет BE NBT), отказ поршней двигать блок, совместимость с модами, двигающими блоки. При 10 000 растений экономия ≈ 0.8 МБ — не стоит. Отклонено (ADR-0003). Пересмотр, если замер покажет > 1 КБ на растение.

### 6.3 Лимит 6 вариантов стака (ADR-0007)

1. **Урожай — отдельный предмет на ступень и сорт** (`wild_carrot_root`, `eastern_carrot`, `carrot`, …): сорт закодирован id предмета, а не NBT.
2. **NBT урожая — только два поля**, и пишет их единственная фабрика `ProduceStacks.create(item, grade, bitter)`. Она нормализует ввод: `bitter && grade > 2 → grade = 2`, а `bitter = false` не пишется вовсе. Получается не больше `{1,2,3,4} ∪ {1b,2b}` = 6 вариантов. Других ключей (геном, время, посадивший, окраска) в урожае нет никогда.
3. **Окраска** (жёлтый, оранжевый, фиолетовый корень) видна на модели растения (`BlockState`, §7) и в тултипе лота, но **не** в NBT урожая. Иначе предел 6 не выдерживается (§21, п. 2).
4. **Переработанные продукты с ванильным id** (хлеб и т. п.) несут только `wildroots:grade` — до 4 вариантов. Предмет без поля считается классом 3.
5. **Геном несут только** лоты, маточники, клоны, плоды-блоки (как BE), кисть и мешочек. Лоты по природе уникальны, для них есть мешочек.
6. **Инвариант-тест:** GameTest собирает урожай с сегрегирующей грядки 5×5 каждого архетипа. Проверяются ≤ 6 различных `ItemStack` на предмет и ≤ 4 у переработки.

**Мешочек для семян** — подкласс `Item`, повторяющий поведение ванильного `BundleItem` 1.20.1: `overrideStackedOnOther` / `overrideOtherStackedOnMe` (положить / достать последний), `getTooltipImage` + клиентский `ClientTooltipComponent` (регистрация в `RegisterClientTooltipComponentFactoriesEvent`), полоса заполнения. Принимает только предметы с тегом `#wildroots:pouchable` (лоты, не инертные). Ёмкость считается по количеству семян (≤ 32) и записям (≤ 32), записи не сливаются, мешочек в мешочек не кладётся. Логика вставки и извлечения работает только на серверной стороне меню, клиент лишь предсказывает (SEC-17). Выпавший и уничтоженный мешочек роняет содержимое один раз (`onDestroyed`). Свой пакет не нужен: всё идёт через ванильные клики в инвентаре.

**Против раздувания NBT вложенностью** (SEC-11, дефолт до подтверждения владельцем): `canFitInsideContainerItems()` → `false`, поэтому мешочек не кладётся в шалкер и bundle (проверено в S14: клики меню, shift, SWAP, drag, воронка, дроппер, capability блока и предмета, bundle в обе стороны). Обход есть только через `Container`-API шалкера (`canPlaceItem`/`setItem`, `new InvWrapper(be)` у сторонних модов), креатив и команды. Семенной банк, анализатор и лаборатория мешочки не принимают и закрывают оба пути: переопределяют и `canPlaceItem`, и `canPlaceItemThroughFace`, а capability отдаёт обёртку с той же проверкой (SEC-11a). **Семенной банк при разрушении роняет содержимое** и не хранит его в NBT предмета. Худший случай после этих мер: пакет меню двойного сундука включает 36 слотов инвентаря игрока, то есть 90 × 16 КиБ ≈ 1.44 МиБ несжатого. Это меньше кадра 2 097 151 Б даже при выключенном сжатии (`network-compression-threshold=-1`), когда кадр ограничивает весь несжатый пакет (SEC-12, S10, S14). Поэтому лимит мешочка 16 КиБ обязателен: мешочек из 32 лотов прежнего состава (28 КиБ) при выключенном сжатии рвал бы соединение каждому, кто откроет двойной сундук (2.54 МБ, S10). Если выделенный сервер запущен без сжатия (`getCompressionThreshold() < 0`), мод при старте пишет одно предупреждение в лог: запас по кадру ×1.4 вместо ×2 со сжатием, а чужие крупные предметы в том же сундуке могут его съесть (дефолт до ответа владельца, `STATUS.md`, «Вопросы по итогам spike»).

**Что видит клиент в NBT лота.** Ванильная синхронизация контейнеров отправляет клиенту полный NBT предмета, поэтому геном лота технически доступен модифицированному клиенту. Урезать NBT через `getShareTag` можно, но креативный инвентарь возвращает серверу клиентскую копию, и геном лотов у игроков в креативе стирался бы. Решение: **лот синхронизируется целиком** (цель ≤ 512 Б, мешочек ≤ 16 КиБ; S10). Тултип при этом строится только из блока `disp` (ключи перевода и аргументы), который сервер пишет при создании и при осмотре (`inspected`/`analyzed`). Клиент генетику не интерпретирует, строки игрока показывает только через `Component.literal` и строку `disp`, не прошедшую проверку формата, пропускает. «Сервер решает» соблюдено, «сервер скрывает» от взломанного клиента — нет. Секрет мира (§4.3) не даёт превратить знание генома в оракул потомства, и с ним Security оценивает риск как Low (`09-security.md` §1.8, §21 п. 6). Растения в мире клиенту геном не отдают вовсе.

## 7. Блоки растений и рендер

Решение: ADR-0004.

### 7.1 Блок на встроенный вид + архетипные блоки для датапачных видов

- **Встроенный вид** (все линии GDD) получает **свой блок** (`wildroots:wild_carrot`, `wildroots:wild_wheat`, …). Блок — экземпляр общего архетипного класса с параметром «вид». Так работают ванильные модели blockstate, имена блоков, ресурспаки и Jade. Это совпадает с решением нарратива «один блок на вид» (`04-narrative.md` §7.9).
- **Датапачный вид** без своего Java-кода использует **архетипный блок** (`wildroots:generic_field_plant`, `generic_tall_plant`, `generic_water_plant`, `generic_vine` + `generic_vine_fruit`, `generic_bush`). Вид лежит в BE, внешний вид — общая модель архетипа, окрашенная цветом из JSON вида через `BlockColor` (клиент читает id вида из BE). Это выполняет метрику 6 видения. Ограничения MVP: деревья, тростник и плоды на стволе — только у встроенных видов; урожай датапачного вида — общий предмет `wildroots:generic_produce` с id сорта в NBT, без Forge-тегов культуры (§21, п. 3).
- JSON вида связывает вид с блоком: `"block": "wildroots:wild_carrot"` (по умолчанию — архетипный блок по `"archetype"`). Валидация проверяет, что блок существует и его архетип совместим с видом.

| Архетип | Класс | Встроенные виды | Особое |
|---|---|---|---|
| `field` | `FieldPlantBlock extends CropBlock` | пшеница, морковь, капуста, свёкла, картофель, лук, томат | `extends CropBlock` нужен фермеру-жителю (§11.6) |
| `tall` (2 блока) | `TallPlantBlock extends CropBlock` + верхняя половина без BE | теосинте | Как ванильный `pitcher_crop` |
| `water` | `WaterPlantBlock` | рис | Растёт в воде глубиной 1 |
| `vine` + `fruit` | `VinePlantBlock`, `VineFruitBlock` | тыква (`gourd_fruit`), арбуз (`watermelon_fruit`) | Плод — блок с `FruitBlockEntity` |
| `cane` | `CanePlantBlock` | тростник | BE только в нижнем блоке колонны |
| `trunk_pod` | `TrunkPodPlantBlock` | какао (`wild_cacao`) | На `#minecraft:jungle_logs`, как ванильное какао |
| `bush` | `BushPlantBlock` | малина | Урон как у ванильного куста ягод |
| `tree` | `FruitTreeTrunkBlock` (BE) + `apple_log`, `apple_leaves`, `apple_fruit` | яблоня (`apple_trunk`) | Листва и плоды без BE |

### 7.2 Свойства `BlockState`

`BlockState` содержит только то, что нужно логике без доступа к BE (у ванильных методов `isRandomlyTicking(state)` и `getAge(state)`/`isMaxAge(state)` нет позиции) и что нужно рендеру:

| Свойство | Значения | Зачем |
|---|---|---|
| `stage` | 0–5 | Рост, форма, модель (GDD §5.1) |
| `size` | 0–3 | Масштаб модели `0.4 + 0.8·P_size` квантуется в 4 ступени (GDD §3.3) |
| `variant` | 0–3 (только у видов с окраской) | Окраска корня или початка |
| `ailing` | bool | Чахлость `V < 0.85` (GDD §3.7) |
| `village` | bool | Метка деревни: её видит фермер (§11.6) |
| `active` | bool | `false` — статичное дикое растение без случайных тиков (worldgen §12.2) |

У моркови это 6 × 4 × 4 × 2 × 2 × 2 = 768 состояний. Модели в blockstate-JSON задаются частичными ключами вариантов, и свойства, которые не влияют на модель (`village`, `active`), не размножают модели. Смена `size`/`ailing`/`variant` происходит только при смене стадии, одним `setBlock`.

**Итог:** клиент рендерит растения ванильным путём (запечённые модели по `BlockState`), без `BlockEntityRenderer`, без `ModelData` и без своих пакетов. Пересчёта фенотипа при рендере нет (GDD §13).

## 8. Data-driven реестры: загрузка, валидация, синхронизация

Решение: ADR-0005.

### 8.1 Что и откуда

| Реестр | Путь в датапаке | Загрузчик |
|---|---|---|
| Виды | `data/<ns>/crop_species/<id>.json` (как в видении) | `SpeciesManager extends SimplePreparableReloadListener` |
| Сорта и ландрасы | `data/<ns>/cultivars/<id>.json` | `CultivarManager` (после видов; зависимость задана порядком регистрации в `AddReloadListenerEvent`) |
| Рецептные роли качества | `data/<ns>/wildroots/quality_roles/<id>.json` — роли ингредиентов по тегам: `main` с весом, `neutral`, `booster` (условие, например «класс ≥ 3») | `QualityRolesManager`. Рецепты (§12) могут задать роли явно (`quality_inputs`, `boosters`) или взять их отсюда |
| Шаблоны деревень | `data/<ns>/wildroots/village_templates/<тип>.json` (веса ландрасов, worldgen §11.2) | `VillageTemplateManager` |
| Ландшафтные данные | configured/placed features, biome modifiers, теги | Ванильные реестры датапака (загружаются при открытии мира) |

**Почему reload listener, а не datapack registry Forge** (`DataPackRegistryEvent.NewRegistry`). У datapack registry есть автосинхронизация и Holder-ссылки, но ошибка в любой записи не даёт открыть мир, а `/reload` её не перечитывает. Видение требует пропускать плохие записи без краша, и авторам датапаков удобно править виды через `/reload`. Цена — своя синхронизация (§8.3).

### 8.2 Валидация и сообщения об ошибках

1. JSON → Codec (DFU, есть в Minecraft). `DataResult.error` превращается в `Problem(file, jsonPath, message)`: например, `wildroots:crop_species/wild_carrot.json: $.quantitative.yield.loci: ожидается целое 1–16, получено "six"`.
2. Затем `DefinitionValidator` движка (§4.4) проверяет смысл.
3. `ERROR` → запись пропускается, и вместе с ней зависящие от неё сорта (с отдельной строкой в логе). `WARN` → подставляется значение по умолчанию.
4. Исключения внутри загрузчика ловятся на уровне записи (`catch (Exception | StackOverflowError)`): одна плохая запись не обрывает загрузку остальных. До Codec файл проверяется на размер (> 256 КиБ → ERROR) и глубину JSON (> 32 → ERROR, итеративная проверка). В лог уходит ≤ 200 строк `Problem` за перезагрузку, дальше — «и ещё N» (SEC-27).
5. Итоговая строка в лог: `Wild Roots: species 15 (0 skipped), cultivars 41 (1 skipped) — see above`. Операторам (`permission ≥ 2`) при входе и после `/reload` приходит одно сообщение в чат, если были ошибки.
6. Готовый результат — неизменяемый `DefinitionsSnapshot`, который атомарно подменяется в конце `apply`. Логика сервера всегда читает целый снимок, полусостояния не бывает. `apply` выполняется на потоке `main` при старте и на `Server thread` при `/reload` (S12), поэтому ссылка на снимок — `volatile` (или `AtomicReference`).

**`/reload` при живом мире.** Растения при перезагрузке не пересчитываются массово. Новая раскладка вида применяется лениво при следующем обращении к растению или предмету (§5.3), новые пороги сортов — при следующей проверке (посадка или созревание). Без сканирования.

### 8.3 Синхронизация с клиентом

Клиенту нужно только то, что показывают UI и рендер. Пакет `DefinitionsSyncPacket` уходит в `OnDatapackSyncEvent` (вход игрока и `/reload`):

| Отправляется | Не отправляется |
|---|---|
| id вида → архетип, ключи перевода, подписи признаков (`display_traits`), цвет для архетипных блоков, жизненный цикл | Частоты аллелей, элитные локусы, `tradeoffs`, `budget`, груз, мутации |
| id сорта → вид, ступень, предмет урожая, ключ справки, `food_reference` (для `getFoodProperties` на клиенте и тултипа) | Пороги профилей (их показывает анализатор строками, которые сформировал сервер) |
| Список загруженных линий | Шаблоны деревень, роли качества |

Размер ≈ 5–15 КБ на 20 видов и 60 сортов. На клиенте снимок неизменяем и сбрасывается при выходе с сервера. Предел — 512 КиБ. Больше — пакет режется на части ≤ 256 КиБ (`part`/`total`). Нарезка своя и обязательна: Forge не разбивает пакеты `SimpleChannel` (`VanillaPacketSplitter` режет только рецепты, теги, достижения и login), а S→C custom payload ограничен 1 048 576 Б (S14). Больше 2 МиБ — ERROR оператору, и датапачные виды сверх лимита не синхронизируются. Клиентский декодер ограничен так же, а ошибка разбора отключает клиента с понятным сообщением, а не роняет игру (SEC-31). Пакет не несёт частот, элитных локусов и порогов (SEC-04).

## 9. Линии и волны выпуска

Решение: ADR-0006.

### 9.1 Линия = встроенный датапак + запись в `LineRegistry`

- **Регистрации (блоки, предметы, BE, меню) — все и всегда**, независимо от волн и конфига. Причины: (1) Forge сверяет реестры клиента и сервера, и выключенная на одной стороне линия рвала бы соединение; (2) мир, где линию выключили, иначе потерял бы блоки (они стали бы воздухом при загрузке чанка); (3) переключение линии — это перезапуск, а не порча мира. Если предмет линии существует, а линия выключена, он инертен: вида нет в определениях (§5.3), в креативной вкладке и в JEI он скрыт (`BuildCreativeModeTabContentsEvent`, JEI `removeIngredientsAtRuntime`).
- **Волна выпуска** = какие пакеты линий лежат в jar. Блоки и предметы линии появляются в коде в той волне, в которой выходит её пакет. Заглушек на будущее нет.
- **Пакет линии** `resourcepacks/lines/<line>/` (пример — `carrot`) содержит: определения вида и сортов, worldgen-модуль (features, теги, biome modifiers `add_features`/`remove_features`), записи тегов `#wildroots:removed_vanilla_crops` и `#wildroots:village_crop_input`, шаблоны деревень, перекрытия ванильных рецептов (`minecraft:golden_carrot` → тип `wildroots:quality_shaped`), рецепты инструментов линии, достижения линии, записи GLM. Перекрытие выигрывает у пакетов модов, установленных до появления линии в мире (S1, §9.2).
- **FD-часть линии** `resourcepacks/lines/<line>_fd/` содержит удаление дикой культуры FD, FD-теги на наши предметы и перекрытия FD-рецептов. Добавляется, только если загружены и линия, и FD.

### 9.2 Механика

```java
// core.line.LinePackFinder — подписан на AddPackFindersEvent (mod bus)
void onAddPackFinders(AddPackFindersEvent e) {
  if (e.getPackType() != PackType.SERVER_DATA) return;
  for (LineId line : LineRegistry.enabled()) { e.addRepositorySource(builtInRequiredPack("lines/" + line)); ... }
}
```

- Пакеты регистрируются как `PackSource.BUILT_IN`, `required = true`, `Position.TOP`. В Forge 47.4.x у каждого мода свой пакет `mod:<modid>` (`mod:forge`, `mod:wildroots`; пакета `mod_resources` нет). Пакет линии встаёт выше всех `mod:*` в новом мире и при первом появлении в старом мире: `MinecraftServer#configurePackRepository` дописывает новые пакеты в конец, а обязательный пакет выбирается, даже если он в `Disabled` у `level.dat` (подтверждено S1, `docs/spikes/S1-line-packs.md`). Порядок сохраняется в `level.dat`: пакет мода, установленного **позже**, встаёт выше пакета линии, и его перекрытие того же ванильного рецепта выигрывает. Это принятое ограничение (дефолт до ответа владельца, `STATUS.md`): конфликт перекрытий ванильных рецептов с другим модом решает порядок установки; это известная несовместимость, она документируется для игроков. Если владелец не примет ограничение, нужен отдельный ADR на переупорядочивание выбранных пакетов (например, mixin в `MinecraftServer#configurePackRepository`); в списке §16 такого mixin нет.
- `LineRegistry` строится при конструировании мода: манифест линий в jar (`wildroots/lines.json`: id, волна, ванильные культуры линии, FD-аналог) минус `CommonConfig.disabledLines`. **`disabledLines` — в COMMON-конфиге, а не в SERVER**: список пакетов собирается до загрузки серверного конфига мира. Смена требует перезапуска. Worldgen и так фиксируется при генерации чанков (worldgen §16.2).
- Код ядра (GLM, процессоры, случайный тик, торговля, запрет посадки) читает `LineRegistry` и теги, собранные из пакетов линий. Своего списка культур в коде нет.
- Условие `wildroots:line_loaded` (`ICondition`, регистрация `CraftingHelper.register` в `FMLCommonSetupEvent#enqueueWork`, как в S1) остаётся для рецептов и достижений **ядра**, которые зависят от линии (например, достижение `vavilov`). Для worldgen и GLM условия не нужны: эти файлы живут в пакетах линий.
- **Режим `strict`/`soft`** — в SERVER-конфиге мира. Пакеты от режима не зависят: всё, что отличается (запрет посадки ванили, вырезание культур чужих модов в GLM), проверяется в коде во время игры.
- **Авторам датапаков:** новая линия — это обычный датапак с той же структурой. Ванильную культуру он убирает своими `remove_features` и тегами, ядро подхватывает теги само.

### 9.3 Поддержка условий в Forge 47.x (вопрос STATUS)

| Где | Поддержка в 1.20.1 | Наше решение |
|---|---|---|
| Рецепты, достижения | Да: ключ `"conditions"` (без префикса; `RecipeManager#apply` → `CraftingHelper.processConditions(json, "conditions", ctx)`), своё условие через `CraftingHelper.register(IConditionSerializer)` — подтверждено S1 для рецептов (достижения не проверялись) | Используем `forge:mod_loaded` и `wildroots:line_loaded` |
| Biome modifiers, placed/configured features (datapack-реестры) | Да: ключ `"forge:conditions"` (`RegistryDataLoader#loadRegistryContents` → `ICondition.shouldRegisterEntry`, контекст `TAGS_INVALID`: условия по тегам не работают), своё `wildroots:line_loaded` работает — подтверждено S1 | Основной механизм прежний: всё лежит в пакетах линий (вариант Б из worldgen §16.2). Условия допустимы как вторичный механизм, например для FD-части линии вместо отдельного пакета `<line>_fd` |
| Global Loot Modifiers | В JSON модификатора `conditions` — это loot-условия (`LootItemCondition`), а не `ICondition` `[ПРОВЕРИТЬ]` | Не полагаемся: модификаторы проверяют линии в коде, а записи `global_loot_modifiers.json` лежат в пакетах линий (список `entries` сливается между пакетами при `replace: false`) |
| Теги | `{"id": …, "required": false}` | Для ссылок на FD и прочие моды |

Пример из `03-worldgen.md` §8.7 с `forge:conditions` в biome modifier рабочий (S1), но по ADR-0006 тот же JSON без условий кладётся в пакет `wild_tomato` FD-линии.

## 10. Рост, случайные тики, опыление, пчёлы, перф-бюджет

### 10.1 Рост

- `isRandomlyTicking(state)` = `state.active` и стадия не финальная для однолетника. Статичные дикие растения и завершённые однолетники не тикают вообще.
- `randomTick`: чтение BE (поиск в карте BE чанка) → кэшированный шанс роста (`growthChance`, его считают при посадке и смене стадии из `P_growth`, `E`, полива) → бросок → при успехе `GrowthLogic.advance`. Это пересчёт `E` и `P` (≤ 100 операций), новый `BlockState` (`stage`, `size`, `ailing`, `variant`) и события стадии: вход в цветение → `BloomIndex.add`, выход → `remove`, переход «цветение → семена» → завязывание (§10.2).
- Перед своей логикой вызывается `ForgeHooks.onCropsGrowPre/Post` (`BlockEvent.CropGrowEvent`): моды-ускорители и защитники регионов видят наш рост как обычный.
- Цветение длится реальное время. Костная мука на цветении не действует, на стадиях 1–3 и 5 даёт +1 стадию с шансом 0.35 (`performBonemeal`).
- Многолетники после сбора возвращаются на стадию 3. Время отрастания `regrow_min` реализовано тем же случайным тиком с пониженным шансом, таймеров нет.
- Покой семян (`dormancy`): стадия 0 с `active` и кэшированным шансом выхода, откалиброванным на `U(2,6)` мин. Таймеров нет.

### 10.2 Индекс цветения и завязывание (ADR-0008)

```
BloomIndex (на ServerLevel, только в памяти)
  Long2ObjectOpenHashMap<ChunkBloom>    ключ = ChunkPos.toLong
  ChunkBloom: Int2ObjectOpenHashMap<LongOpenHashSet>  speciesIndex → packed BlockPos (удаление O(1), SEC-33)
```

- **Наполнение:** вход в цветение (смена стадии) и `PlantBlockEntity.onLoad` для цветущих (включая статичные дикие, worldgen §12.2). **Очистка:** выход из цветения, `setRemoved`, `onChunkUnloaded`, `LevelEvent.Unload`. Индекс не сохраняется: он восстанавливается сам при загрузке чанков, рассинхрона с диском не бывает.
- **Завязывание (один раз за цикл):** кандидаты берутся из `ChunkBloom` чанков, которые пересекает круг `radius` вида (при `radius ≤ 8` это ≤ 4 чанка), с фильтром `±2` по Y, до 64 кандидатов (reservoir sampling). Запрос посещает не больше 1024 записей индекса (SEC-33). У кандидата читается BE только через `LoadedLevelAccess`: соседние чанки никогда не загружаются (SEC-32), а выгруженный чанк — это «пусто». Затем копируется геном. Дальше `GeneticsService.chooseFathers`, к которому добавляются ≤ 4 донора от пчёл и кисти, уже лежащие в BE. Результат — «ожидающий лот» в BE. Отцы копируются **по значению**: сломанный позже отец остаётся донором (GDD §14).
- **Сломали без сбора семян** (поршень, вода, взрыв) — лот без отцов (GDD §14): `HarvestService` различает игрока с пустой или любой рукой (обычный сбор) и прочие причины.

### 10.3 Пчёлы (ADR-0009)

Без mixin. Ванильный `BeePollinateGoal` ищет цели по тегу `#minecraft:flowers`. Тег не различает состояния блока (стадия цветения) и виды, поэтому для нас не подходит. Вместо этого:

1. `EntityJoinLevelEvent` (сервер): каждой `Bee` добавляется наша цель `BeeCropPollinateGoal` с тем же приоритетом, что у ванильной цели опыления (4) (`goalSelector.addGoal`; поле `Mob.goalSelector` в 1.20.1 — `public final`, AT не нужен; S2, `docs/spikes/S2-bee-goal.md`). Цель добавляется при каждом входе сущности в мир, включая выход из улья, с проверкой `getAvailableGoals()` против дубля.
2. **Выбор цели без сканирования:** когда пчеле нужен нектар (`!hasNectar()`, вне улья, кулдаун истёк), цель запрашивает `BloomIndex` чанка пчелы и соседних (радиус как у ванильного поиска цветов, ~5 блоков) и берёт цветущее растение вида, у которого в JSON есть `bees`. Если такого нет, цель не стартует, и работает ванильная цель с цветами. Это O(записей в 1–4 чанках), а не перебор блоков. Пчела запрашивает индекс не чаще раза в 20 тиков, на уровень приходится ≤ 64 запросов пчёл за тик, лишние откладываются (SEC-33). Запрет GDD §13 «поиск растений вне ванильного AI» я трактую как запрет сканирования мира. Запрос к индексу — это не скан (§21, п. 7).
3. **Визит:** подлёт и зависание по образцу ванильной цели (≈ 400 тиков) → `PollinationService.beeVisit(bee, plant)`: при свежей пыльце (≤ 2 визитов, ≤ 1200 тиков **жизни пчелы вне улья**: счётчик в `BeePollen` растёт в `LivingTickEvent` и не идёт, пока пчела в улье) того же вида от другого растения в BE пишется донор (вес 2.0, вытесняется старейший). По мировому времени окно недостижимо: после визита пчела с нектаром сидит в улье ≥ 2400 тиков и не выходит ночью, поэтому между визитами проходит ≥ 2850 мировых тиков (S2). Счёт вне улья — дефолт **до подтверждения GD** (правка GDD §4.3 после ответа, `STATUS.md`). Затем пыльца пчелы заменяется пыльцой этого растения, и пчела получает нектар (`setHasNectar(true)`; метод package-private → AT `public net.minecraft.world.entity.animal.Bee m_27919_(Z)V`, S2). `tick()` цели идемпотентен после визита: `GoalSelector` перепроверяет `canContinueToUse` раз в 2 тика, и следующий `tick()` приходит раньше `stop()` (в S2 это дало NPE).
4. **Пыльца** — capability `BeePollen` на `Bee` (`AttachCapabilitiesEvent<Entity>`). Она сериализуется вместе с сущностью, в том числе когда пчела сидит в улье: улей хранит NBT сущности вместе с `ForgeCaps` (`BeehiveBlockEntity#removeIgnoredBeeTags` их не вырезает; S2). UUID вырезается: из улья выходит новая сущность, поэтому ссылки на пчёл по UUID не хранятся.
5. `bee_growables` не трогаем: наши блоки не входят в тег, и ванильный бонус роста на них не действует (GDD §4.3).
6. **Запасной путь**, если spike покажет, что две цели конфликтуют (пчёлы зависают или игнорируют цветы): один mixin в `Bee.BeePollinateGoal` с предикатом цели и хуком завершения визита. Решение — по итогам spike S2 (§20). S2: конфликта нет (0 зависаний нашей цели за 3 игровых дня, при равном приоритете и флаге `MOVE` цели друг друга не вытесняют), M5 не нужен.

### 10.4 Кисть

Кисть — `Item.useOn` на сервере. Пыльца в NBT кисти: вид, копия генома, срок. Повторное применение заменяет донора `p_out = 0.90`. Самоопыление и бутонное опыление у самонесовместимых видов задаются флагами. Пакетов нет.

### 10.5 Оценка бюджета: 10 000 растений, `randomTickSpeed = 3`

| Источник | Частота | Стоимость | мс за тик |
|---|---|---|---|
| Случайные тики по растениям | 10 000 × 3/4096 ≈ 7.3 за тик | 1–3 мкс (BE-lookup + бросок) | 0.01–0.02 |
| Смены стадии | ≈ 5 смен × 10 000 / (11 мин × 1200) ≈ 3.8 за тик | 15–30 мкс (`setBlock`, соседи, свет, пакет блока, пересчёт `P`) | 0.06–0.11 |

| Посадка (мейоз ~60 локусов, классификация, фенотип) | По действию игрока, ≈ 0.5 за тик в пике посадки | 10–20 мкс | ≤ 0.01 |

| Индекс цветения | Только на сменах стадии и загрузке чанков | O(1) | ≈ 0 |
| Жители-фермеры | Ванильный обход + пересадка шаблоном (1 генерация генома) | Как ванильный сбор | ≈ 0 сверх ванили |

Запас ≈ ×10 к бюджету 2 мс. Большая часть затрат — ванильный `setBlock`, его же платит ванильная пшеница. Проверка — стенд в spike S9: мир с 10 000 растений в 40 чанках с теплицами, `spark` по `wildroots`, приёмка — прирост MSPT ≤ 2 мс против той же площади ванильной пшеницы.

**Риски перфа и меры:** (1) массовая загрузка чанков с тысячами BE — `onLoad` делает только регистрацию в индексе, геном не декодируется (ленивое декодирование NBT → `Genome` при первом обращении); (2) автосохранение — §6.2; (3) Jade на клиентах — данные провайдера считаются только по наведению.

### 11.2 Ванильные культуры: посадка, старые чанки, worldgen

- **Запрет посадки** (`strict`): `BlockEvent.EntityPlaceEvent` отменяет установку блоков из `#wildroots:removed_vanilla_crop_blocks` любым источником, включая фейковых игроков. `PlayerInteractEvent.RightClickBlock` с семенами из `#wildroots:removed_vanilla_crops` → `setUseItem(DENY)` и сообщение «нужен посадочный материал». FD-семена — через тот же тег (`required: false`).
- **Старые чанки и модовые деревни:** `BlockEvent.CropGrowEvent.Pre` — Forge вызывает его из `randomTick` ванильных `CropBlock`, `StemBlock`, `SugarCaneBlock`, `CocoaBlock`, `SweetBerryBushBlock` `[ПРОВЕРИТЬ]` полный список вызовов в 47.x. Если блок в теге загруженной линии, событие отменяется, а блок заменяется живым растением. **Ландрас с `village = true`** ставится только при двух условиях (SEC-23): чанк сгенерирован **до** включения линии (в маркере чанка `wr_lines` её нет; маркер пишет наша генерация, у чанков, созданных до установки мода, его нет вовсе) **и** в радиусе 32 есть POI `minecraft:meeting` (колокол). Результат POI-запроса кэшируется на чанк на 1200 тиков. Кровать или компостер игрока поле деревенским не делают. Во всех остальных случаях получается дикое растение по биому (worldgen §11.4) с меткой `wild`. Бюджет — ≤ 16 конверсий на уровень за тик, остальные ждут следующего случайного тика (SEC-35). Сканирования нет, и mixin тоже нет.
- **Глобальный процессор шаблонов `vanilla_crop_scrub`** (worldgen §11.4) требует mixin в `StructureTemplate` — у Forge нет хука на все шаблоны. **В MVP не делаем**: процессоры ферм (§11.7), случайный тик выше и GLM на дроп закрывают культуры, которые тикают или ломаются. Ванильные плоды-декор в чужих структурах остаются до сбора и роняют лот. Mixin добавляется, только если плейтест покажет утечку (§21, п. 8).
- **Генерация:** `forge:remove_features` / `forge:add_features` в пакетах линий (§9). Какао-декоратор: перекрытие `minecraft:jungle_tree` и родственных configured features в пакете линии какао (worldgen §9.1) с тем же риском порядка загрузки, его страхует случайный тик.
- **Лиса со сладкими ягодами** (worldgen §15.1 №10): `EntityJoinLevelEvent` (серверная лиса, предмет в руке в теге) → замена на `wild_raspberry`.

### 11.3 Торговля

- **Фермер:** `VillagerTradesEvent` с `EventPriority.HIGHEST` для `VillagerProfession.FARMER` очищает списки уровней и строит их заново из наших `ItemListing`. Другие моды добавляют свои сделки позже, на обычном приоритете, и их записи не теряются. Наши листинги **ленивые**: `getOffer(entity, random)` смотрит `LineRegistry` и, если линии нет, отдаёт ванильную сделку этой культуры. Так волны работают без пересборки списков (economy §11). События постятся один раз за запуск сервера (Forge `VillagerTradingManager`, `ServerAboutToStartEvent`), уже после первой загрузки reload listener'ов, и на `/reload` не повторяются. Таблицы перестраиваются из копии ванильных при каждом запуске, поэтому повторный вход в мир сделки не дублирует. Предложения, которые житель уже сгенерировал, хранятся в его NBT и после `/reload` не меняются; новые берутся из нового снимка (S12, `docs/spikes/S12-trade-events.md`).
- **Селекционер:** тот же механизм для `wildroots:plant_breeder`. Лимиты сделок, опыт и цены — из `02-economy.md` §6.5.
- **Странствующий торговец:** `WandererTradesEvent`. Ванильные листинги **оборачиваются** в `FilteringListing`: если результат или цена в `#wildroots:removed_vanilla_crops`, листинг отдаёт подменную сделку с первородным лотом вместо `null`, чтобы число предложений не уменьшалось. Наши сделки (первородные и «хранимые» лоты) добавляются.
- **Лоты в сделках — ленивые** (`tpl`, §6.1): у каждой покупки свой `lotId` при реализации на сервере.
- **«Покупаю урожай любого класса»:** цена без NBT. Ванильный `MerchantOffer.satisfiedBy` при цене без тега принимает предмет с любым тегом `[ПРОВЕРИТЬ]`.
- **Сделки с динамическим результатом и потреблением всего лота** (ADR-0015, SEC-19…SEC-22). «Оценка семян» (лот на входе → тот же лот с флагами на выходе), «редкая находка» и «свой ландрас» (сделка забирает весь стак) не укладываются в ванильный `MerchantOffer` с фиксированным результатом. Требования: результат и списание считаются **в момент взятия** на сервере из фактической оплаты; одна продажа на `lotId` (`wildroots_sold_lots`); потолок находок на игрока (`breederRareFindDailyCap`, по умолчанию 6, окно `floor(gameTime / 24000)`, проверка до сделки, счётчик в capability игрока и клиенту не синхронизируется); ступень 2 никогда не продаётся и не покупается, и это проверяется в коде (SEC-24). Механизм выбирает **spike S13**: (а) подкласс `MerchantOffer` с маркером в NBT предложения — проверить, что маркер переживает сохранение жителя и `ClientboundMerchantOffersPacket`; (б) Forge `TradeWithVillagerEvent` `[ПРОВЕРИТЬ]` наличие и момент вызова в 47.x; (в) mixin **M7** в `MerchantResultSlot`/`MerchantContainer`; (г) **запасной путь без mixin** — меню услуг на сортировочном столе рядом с селекционером: «оценка семян» и приём находок как машина с серверным инвентарём, с полным контролем над дюпом (SEC-14, SEC-15). Если S13 не даст надёжного (а) или (б), я рекомендую (г), а не M7.
- **3 сделки на уровень** (economy П23, дефолт владельца «да»). В 1.20.1 число зашито в `Villager.updateTrades` (`addOffersFromItemListings(…, 2)`), поэтому нужен mixin `@ModifyArg` только для `farmer` и `plant_breeder` (§16, M4). Запасной путь без mixin — «пул 3, выбор 2» (economy §6.1).

### 11.4 Профессия селекционера и POI

- `DeferredRegister<PoiType>` (`ForgeRegistries.POI_TYPES`): `wildroots:sorting_table` — все состояния блока `sorting_table`, `maxTickets = 1`, `validRange = 1`. Forge сам заполняет карту «состояние → POI» `[ПРОВЕРИТЬ]`.
- Тег `data/minecraft/tags/point_of_interest_type/acquirable_job_site.json` += `wildroots:sorting_table`. Без него безработный не берёт профессию.
- `DeferredRegister<VillagerProfession>`: `wildroots:plant_breeder`, `heldJobSite`/`acquirableJobSite` = наш POI, звук работы ванильный (`VILLAGER_WORK_FARMER` или свой).
- Текстура `assets/wildroots/textures/entity/villager/profession/plant_breeder.png` (+ `profession_level`). Ключ имени `entity.minecraft.villager.wildroots.plant_breeder` — так Minecraft строит его для профессии не из пространства `minecraft` `[ПРОВЕРИТЬ]`.
- Зомби-жители получают случайную профессию из реестра `[ПРОВЕРИТЬ]`, поэтому зомби-селекционер возможен. Вылеченный сохраняет торги (GDD §9.6, edge case).

### 11.5 Деревни: процессоры ферм

- `wildroots:landrace_farm` — `StructureProcessorType` через `DeferredRegister` (`Registries.STRUCTURE_PROCESSOR`). Процессор не пишет геном. Он ставит блок вида с `village = true` и BE NBT с паспортом (`landrace`, `villagePos`, метка), а геном реализуется лениво (worldgen §11.3). Позиция начала структуры процессору недоступна `[ПРОВЕРИТЬ]`, поэтому `villagePos` — это позиция элемента-фермы (`StructurePlaceSettings`/`pivot`), как в запасном варианте worldgen.
- Перекрытие `minecraft:farm_<тип>` и `zombie_<тип>` (копия ванильных процессоров + наш) лежит в пакетах линий. Список ландрасов процессор берёт из `village_templates` только загруженных линий.
- Кучи `pile_pumpkin`/`pile_melon` перекрываются плод-блоками ландраса в пакете линии тыквы и арбуза (worldgen §9.1). Вопрос worldgen §15.2 №4: я рекомендую плод-блоки (BE без тикера и без генома до касания, нагрузка ничтожная).

### 11.6 AI жителей-фермеров для геномных культур (ADR-0010)

Как работает ванильный фермер в 1.20.1 (проверено S3, `docs/spikes/S3-farmer-crop.md`, javap `HarvestFarmland`): поведение из рабочего пакета (`VillagerGoalPackages`) стартует, если `mobGriefing` (хук Forge), профессия `FARMER` и есть память `SECONDARY_JOB_SITE` (пашня в ±4 по X/Z и ±2 по Y от жителя, `SecondaryPoiSensor`). Оно берёт клетки 3×3×3 вокруг самого жителя. Клетка годится, если `block instanceof CropBlock && crop.isMaxAge(state)` (`isMaxAge` — `final`, равен `getAge(state) ≥ getMaxAge()`) или если это воздух над `FarmBlock`. Зрелую культуру фермер ломает через `level.destroyBlock(pos, true, villager)` (дроп считается до установки воздуха, BE ещё доступна). На пустую пашню сажает семена из инвентаря с тегом `#minecraft:villager_plantable_seeds` (`defaultBlockState()` блока `BlockItem`; ветка Forge — `IPlantable` с `PlantType.CROP`). В тике сбора посадки не бывает: обе проверки читают состояние до `destroyBlock`.

Встраиваемся без mixin (S3: подтверждено, запасной путь R3 не нужен):

1. **Сбор только деревенских растений.** `FieldPlantBlock extends CropBlock` переопределяет `getAge(state)`: `getMaxAge()` при `state.village && зрелость(stage)`, иначе `min(stage, getMaxAge() − 1)`. Переопределить сам `isMaxAge` нельзя: в 1.20.1 он `final` (S3). Так как ванильные `randomTick`, `growCrops`, `getStateForAge` (он строит состояние от `defaultBlockState()` и сбрасывает остальные свойства), `isValidBonemealTarget`, `isRandomlyTicking` и `getShape` опираются на `getAge`, блок переопределяет их на своей стадии. Моды-комбайны и подсказки Jade/WTHIT, которые читают `getAge`, увидят спелое растение игрока как `max − 1`. Для встроенного вида стадию урожайной зрелости знает сам блок (двулетник — 3, однолетник — 5). Архетипный блок датапачного вида получает отдельное свойство `ripe`. Растения `player` и `wild` для фермера всегда «незрелые», он их не трогает (GDD §9.5 п. 4). Топтание пашни ломает любую культуру, как в ванили.
2. **Урожай в инвентарь жителя.** В `getDrops(BlockState, LootParams.Builder)`, если ломающий (`LootContextParams.THIS_ENTITY`) — `Villager` с профессией `farmer` (не `FakePlayer`), а `BLOCK_ENTITY` несёт валидный паспорт, урожай ландраса (класс по фенотипу) кладётся в `villager.getInventory()`. Лот не создаётся. Остаток возвращается как дроп.
3. **Пересадка только на деревенской клетке, через очередь.** `Level.destroyBlock` считает дроп до `setBlock(air)`, поэтому в обработчике дропа клетка ещё занята. Пересадка ставится в очередь уровня (позиция + копия паспорта с `harvestCount + 1`) и выполняется в `TickEvent.LevelTickEvent` (фаза `END`) того же тика, если клетка — воздух над `FarmBlock`: новое растение по шаблону ландраса, стадия 0, метка `village`. Это происходит до следующего `HarvestFarmland.tick`, так что ванильная посадка семян на эту клетку не успевает (S3). Очередь только в памяти: при остановке сервера в середине тика клетка останется пустой пашней — это не потеря данных. Семена в инвентаре жителю не нужны, а наши лоты тег `villager_plantable_seeds` не получают. Ванильные `carrot`/`potato`/`wheat_seeds`/`beetroot_seeds` в теге остаются: фермер с ними в инвентаре сажает ванильную культуру на любую пустую пашню рядом с собой, в том числе на пашню игрока (ванильное поведение; дефолт — принять, `STATUS.md`). Такая культура дальше идёт по правилам §11.2 (`CropGrowEvent.Pre`).
4. **Ответ на П16 (`village_farmland`):** отдельный флаг на пашне не нужен. **Деревенская клетка — это наше растение с `village = true`**. Его ставят только (SEC-23): процессор `landrace_farm` при генерации; делянка хижины; пересадка **существующей** деревенской клетки фермером; конверсия старой ванильной культуры в чанке, сгенерированном до включения линии, рядом с колоколом (§11.2). `isMaxAge`/`getAge` видят только `BlockState`, поэтому подделку (`village = true` без валидного паспорта в BE, например после `setblock` или из подделанного шаблона) фермер ломает. Защита: (1) обработчик дропа без валидного паспорта не кладёт урожай в инвентарь и не ставит пересадку — урожай падает на землю (проверено S3); (2) `onPlace` планирует тик через 1 тик (`scheduleTick`), который снимает `village` при невалидном паспорте (BE из шаблона к этому моменту уже загружена; в S3 не проверялось, проверяет WR-165). Урожай в инвентарь и пересадка срабатывают, только если `THIS_ENTITY instanceof Villager` с профессией `farmer`. `FakePlayer` жителем не считается. Когда игрок собирает деревенское растение, на клетке остаётся «жнивьё» — отдельный блок `wildroots:village_plot` (`extends CropBlock`, BE с паспортом деревни: ландрас, `villagePos`, `harvestCount`). У него `getAge` всегда равен `getMaxAge()` (блок не тикает и дропа не даёт), поэтому фермер при обходе его «собирает», и очередь ставит на клетку новое растение шаблона (S3). Отдельный блок нужен потому, что свежепосаженное деревенское растение (стадия 0) нельзя отличить от жнивья по `BlockState`, а фермер видит только его. Если игрок ломает жнивьё или сажает в клетку свой лот, клетка выходит из деревенского фонда. Кран ограничен исходным полем, ровно как в П16. Пашня игрока никогда не становится деревенской: метку ставит только worldgen.
5. **Двулетники** у жителя не цветут: он собирает их на стадии 3. Несобранное растение цветёт и участвует в опылении как любое другое (GDD §9.5 п. 5–6).
6. **Еда жителей** — `Villager.FOOD_POINTS` и `WANTED_ITEMS` в 1.20.1 — это неизменяемые статические коллекции в коде, без событий. Нужен mixin M1 (§16): `countFoodPointsInInventory` и `eatUntilFull` считают очки **по стаку** (тег `#wildroots:villager_food`, класс хлеба по economy §6.7), `wantsToPickUp` принимает тег, `TradeWithVillager#tick` добавляет тег в набор, которым жители делятся (`throwHalfStack`). Подмена самих коллекций через AT не подходит: ключ — `Item`, а очки хлеба зависят от класса (S4, `docs/spikes/S4-mixin-points.md`). Обмен едой нужен потому, что урожай ландраса собирает только фермер: без M1d остальные жители его не получают и не размножаются. Без него жители в `strict` теряют размножение, как только линия забирает их ванильную еду.
7. **Малина на `coarse_dirt`** (worldgen §15.2 №3): `HarvestFarmland` смотрит только клетки над `FarmBlock` и культуры `CropBlock`. Куст малины на `coarse_dirt` фермер не тронет: он просто растёт и даёт урожай игроку. Пересадки нет, но и нужды в ней нет (куст многолетний).

### 11.7 Хижина селекционера и «≤ 1 на деревню» (ADR-0011)

В jigsaw 1.20.1 нельзя ограничить число элементов пула. Сравнение вариантов:

| Вариант | Гарантия ≤ 1 | Код | Риски |
|---|---|---|---|
| А. Свой тип элемента + mixin в `JigsawPlacement.Placer` (пропуск, если хижина уже есть в `pieces`) | Да | Mixin во внутренний приватный класс | Конфликты с модами, которые тоже меняют jigsaw |
| **Б. Хижина как вариант стартового элемента** (`village/<тип>/town_centers`): своя «площадь с хижиной селекционера» — свой шаблон с колоколом, точкой сбора, соединителями улиц и хижиной | **Да, по построению**: у деревни ровно один стартовый элемент | Добавить элемент в пул из кода на `ServerAboutToStartEvent` (AT на поля `StructureTemplatePool`: `templates` и `rawTemplates` `[ПРОВЕРИТЬ]` имена) | Хижина всегда у центра деревни. Шаблон площади — наша работа, копии ванильных NBT не нужны |
| В. Низкий вес в пуле домов | Нет (≈ 2 % деревень с двумя) | Нет | worldgen §11.5 уже отклонил |

**Решение: Б.** Частота «≈ 1 из 5» задаётся точно: вес наших стартовых элементов = 25 % от суммы весов незомби-элементов пула (тогда доля 20 %). Зомби-варианты стартовых элементов не трогаем, так что хижин в зомби-деревнях нет. Добавление в пул выполняется, только если загружена линия пшеницы (волна 2). Отделка под 5 типов деревень. Это отклонение от worldgen §11.5 («дом в пуле домов») — его должен принять Level Designer (§21, п. 4). Если не примет — вариант А с mixin M6.

Лут бочек — `wildroots:chests/breeder_hut/<тип>`. Таблички с переводимыми компонентами в шаблоне — `[ПРОВЕРИТЬ]` (worldgen §11.5). Запасной путь — пустые таблички, а надпись ставит процессор при размещении.

## 12. Переработка с качеством, еда, корм

Решение: ADR-0012.

### 12.1 Ванильные станции: свои recipe serializers

Ванильные рецепты перекрываются **по их же id** в пакете линии (`data/minecraft/recipes/bread.json` с `"type": "wildroots:quality_shaped"`). Ингредиенты в перекрытии — теги, результат — ванильный id (GDD §6.5–6.6).

| Тип | Базовый класс | Что добавляет JSON |
|---|---|---|
| `wildroots:quality_shaped` | `ShapedRecipe` | `quality_inputs` (символы ключа или роли из `quality_roles`), `boosters`, `output_by_grade` (технические продукты: бумага 1/2/3/3, сахар 0/1/1/2) |
| `wildroots:quality_shapeless` | `ShapelessRecipe` | То же |
| `wildroots:quality_smelting` / `_smoking` / `_campfire` | `SmeltingRecipe` / `SmokingRecipe` / `CampfireCookingRecipe` | `quality_inputs` (один вход) |

- `assemble(container, registryAccess)` читает классы и ступени входов: класс из `wildroots:grade` (нет поля → 3, горький → 1), ступень — из тегов `wild_produce`/`landrace_produce`/`cultivar_produce`. Затем вызывает `GeneticsService.process` и пишет `wildroots:grade` в результат. Класс виден уже в слоте результата.
- `matches` возвращает `false`, если по классу выход равен 0 (сахар из ландраса класса 1). Пустого результата в сетке нет.
- Работает везде, где вызывается `assemble`: верстак (слот результата и Shift-клик проверены в S5, `docs/spikes/S5-furnace-quality.md`), печь (Forge-патч). **Книга рецептов не раскладывает ингредиенты с NBT** (`ServerPlaceRecipe` берёт «чистый» стак, `Inventory#findSlotMatchingUnusedItem` сравнивает через `isSameItemSameTags`), поэтому урожай с классом через неё не крафтится: игрок кладёт его в сетку вручную. Это ограничение ванили, известное и для переименованных предметов; mixin его не обходит. Автокрафтеры модов (Create, AE2, RS) не проверены. JEI и книга рецептов показывают `getResultItem` без класса, то есть «добротный», и это нормально.
- **Печь, коптильня:** Forge 47.x вызывает в печи `assemble(this, registryAccess)`, но выходной слот сравнивает без NBT (`canBurn`: `ItemStack.isSameItem`; `burn`: `is(Item)` + `grow`). Классы сливаются: картофель класса 4 попал в стопку класса 1, класс 4 потерян (S5). Решение без mixin: `quality_smelting`/`_smoking` возвращают `matches = false`, если в слоте 2 лежит тот же предмет другого класса (печь передаёт в `getRecipeFor` сам BE, поэтому `matches` видит выходной слот). Печь ждёт, пока результат заберут, и класс не теряется (S5). Побочный эффект: вход, положенный в заблокированную печь, готовится 200 тиков вместо значения рецепта (косметика). M3 остаётся запасным путём, если защита в `matches` конфликтует с чужими рецептами на тот же вход (другой мод может перехватить плавку, пока наш рецепт заблокирован; не проверено). У `_campfire` защита не нужна: костёр роняет результат на землю.
- **Торт** — блок без BE: класс не переносится, торт всегда класса 3 (economy П26, запасной вариант принят). **Блок арбуза** — то же.
- **Цепочка останавливается** (книга, карта, ракета): ванильные рецепты не трогаем, NBT бумаги в них не учитывается.
- **Ингредиенты с NBT подходят во все ванильные рецепты** (ванильный `Ingredient` NBT не смотрит), в том числе в варку зелий (`PotionBrewing` сравнивает предмет) `[ПРОВЕРИТЬ]`.

### 12.2 Farmer's Delight: хрупкость хука и запасной путь

| Станция FD | Хук класса | Хрупкость | Решение MVP |
|---|---|---|---|
| Разделочная доска (выход по классу) | **Данными, без кода:** рецепты на класс через ингредиенты Forge `forge:partial_nbt` (класс 3 и 4) и `forge:difference` (база минус классы 3–4) `[ПРОВЕРИТЬ]` наличие `DifferenceIngredient` в 47.x и разбор ингредиентов FD через `CraftingHelper.getIngredient` | Низкая: публичный формат JSON | **Делаем:** классы 1–2 → 1 ломтик, 3–4 → 2 |
| Котёл (класс блюда) | Подкласс `CookingPotRecipe` с нашим сериализатором и тем же типом рецепта FD. Работает, только если `CookingPotBlockEntity` берёт результат через `assemble`, а не через `getResultItem`, и не сливает буфер блюда без сравнения NBT `[ПРОВЕРИТЬ]` по исходникам FD 1.20.1 | Высокая: внутренний код FD, меняется между версиями | **Запасной путь по умолчанию** (дефолт владельца «да»): блюда FD без класса (= 3). Весь FD-код живёт в `compat.fd` (§13). Если FD нет, классы этого пакета не загружаются.

### 12.3 Еда

- **Наши предметы** (`ProduceItem`, маточники) переопределяют `getFoodProperties(stack, entity)`: `n = max(1, round(n_ref·m))`, `s = s_ref·m`, горечь — ×0.5 к насыщению плюс эффект тошноты или отравления. `FoodProperties` кэшируются на (предмет, класс, горечь), это ≤ 6 объектов. `n_ref`/`s_ref` приходят из `food_reference` сорта (синхронизируются, §8.3). Базовые `FoodProperties` при регистрации нужны только для `isEdible()` и длительности поедания.
- **Ванильные id с классом** (хлеб, пирог, печенье, печёный картофель, свекольный суп, кроличье рагу, золотая морковь, золотое яблоко): у Forge 47.x нет события «свойства еды» (S4: свойства еды есть только в `IForgeItem`/`IForgeItemStack#getFoodProperties`, а `LivingEntityUseItemEvent.Finish` срабатывает уже после начисления). Нужен mixin M2 в `FoodData#eat(Item, ItemStack, @Nullable LivingEntity)` — метод добавлен патчем Forge и не имеет SRG-имени, поэтому `@Inject(HEAD, cancellable, remap = false)`: если у стака есть `wildroots:grade`, ванильные `n`/`s` умножаются на коэффициент класса. Тултип показывает класс через `ItemTooltipEvent` (без mixin). AppleSkin и похожие моды покажут ванильные числа — известное ограничение.

### 12.4 Корм животных — события, без mixin

`Animal.isFood` в 1.20.1 зашит в каждом классе. Тегов `pig_food` и т. п. в этой версии ещё нет `[ПРОВЕРИТЬ]`; `#minecraft:fox_food` есть.

- **Размножение и лечение:** `PlayerInteractEvent.EntityInteract` (сервер). Если предмет в `#wildroots:feeds/<тип>` и животное может войти в «любовь» (`canFallInLove`, возраст), вызывается `setInLove(player)`, предмет тратится, событие отменяется. Лошади: лечение и рост — по ванильной таблице их корма.
- **Приманивание:** `EntityJoinLevelEvent` добавляет `TemptGoal` с `Ingredient.of(tag)` к тем же видам.
- **Лисы:** тег `#minecraft:fox_food` += малина. Куры и попугаи — так же через события.

### 12.5 Класс в торговле и в сундуках

Продажи жителей с классом 2 (хлеб, пироги фермера) создают результат через `ProduceStacks`/`GradedStacks`. Сундуки — GLM `grade_processed` (§11.1).

## 13. Опциональная совместимость

**Общий шаблон soft-dependency:**
- `mods.toml`: `[[dependencies.wildroots]] modId = "<mod>" mandatory = false versionRange = "[<min>,)" ordering = "AFTER" side = "BOTH"`. В 1.20.1 это `mandatory`, а не `type` `[ПРОВЕРИТЬ]`.
- Gradle: `compileOnly fg.deobf(api)` + `runtimeOnly fg.deobf(full)` — полный мод только в dev-запусках.
- Классы чужого мода импортируются только в `compat.<mod>`. Вход в пакет — из общего кода через `if (ModList.get().isLoaded("<mod>")) CompatFd.init(bus)`, где `CompatFd` — единственный класс-мост, и его импорты не тянут FD при загрузке вызывающего класса.
- Плагины, которые чужой мод находит по аннотации (`@JeiPlugin`, `@WailaPlugin`), живут в `compat` и без мода не загружаются вовсе.

| Мод | Что делаем | Где |
|---|---|---|

Линии томата, лука и риса загружаются, только если FD есть (`LineRegistry` учитывает `requires_mod` в манифесте) | `compat.fd`, пакеты `*_fd` |

## 14. Сеть

Решение: ADR-0013.

- **Канал:** `NetworkRegistry.newSimpleChannel(new ResourceLocation("wildroots", "main"), () -> PROTOCOL, PROTOCOL::equals, PROTOCOL::equals)`. `PROTOCOL` = `"1"` и поднимается при любом несовместимом изменении. Клиент без мода к серверу с модом не подключится, и это ожидаемо: мод обязателен с обеих сторон.
- **Сначала ванильные механизмы:** `BlockState` для рендера, синхронизация контейнеров для предметов, `ServerboundContainerButtonClickPacket` (`clickMenuButton`) для кнопок машин, `NetworkHooks.openScreen` с буфером доп. данных для открытия экранов с результатами анализа, которые посчитал сервер.

| Пакет | Направление | Когда | Содержимое |
|---|---|---|---|
| `DefinitionsSync` | S→C | `OnDatapackSyncEvent` | §8.3 |
| `JournalSync` | S→C | Вход, дельты при открытии записей | id записей, записки, имена сеянцев игрока |
| `Toast` | S→C | Первый сорт, новый вид, необычное растение | Ключ перевода + аргументы |
| `AnalysisResult` | S→C | Завершение анализа (если экран открыт) | Строки, которые сформировал сервер |
| `NameSelection` | C→S | Имя нового сорта-сеянца в журнале | `selectionId`, строка |
| `JournalAction` | C→S | Отметить прочитанным, закрепить | id записи |

**Правила для пакетов C→S** (`09-security.md` §1.6.1):
1. **Общий guard.** Все C→S обработчики регистрируются только через `ServerPacketGuard.register(type, handler)` (SEC-01). Guard проверяет, что `ctx.getSender() != null` и игрок не отключён, выполняет работу в `ctx.enqueueWork(...)`, перехватывает `RuntimeException` при декодировании и обработке (пакет отбрасывается, в лог идёт одна строка) и всегда ставит `setPacketHandled(true)`. Регистрировать в обход guard запрещено, это проверяет ArchUnit.
2. **Клиент передаёт только намерение** (SEC-04): в C→S пакетах — только идентификаторы и строки (`long`, `int`, `boolean`, `String`, `ResourceLocation`). Никаких геномов, классов, флагов, `ItemStack`, количеств и координат для изменения мира.
3. **Декодирование ограничено до аллокации** (SEC-03): `readUtf(max)` с лимитом поля, длины коллекций проверяются до создания массива, лишние байты в буфере → пакет отбрасывается. `readUtf(max)` проверяет байты ≤ 3·max до декодирования, затем `String.length()` ≤ max в UTF-16 code units, а не в кодовых точках (S14). Поэтому `max` = 2 × лимит поля в кодовых точках, а сам лимит в кодовых точках проверяет `PlayerText` после чтения. C→S пакет мода целиком ≤ 32 767 Б (`ServerboundCustomPayloadPacket`).
4. **Единый санитайзер текста игрока** `PlayerText.sanitize(s, maxCodePoints)` (SEC-07): NFC, удаление `§` и кодов форматирования, отказ при управляющих, bidi, zero-width и приватных символах, разрешены буквы, цифры, пробел и `- ' ’ . , ( ) &`; имя сорта — 1–24 кодовые точки, `line_name` с наковальни — ≤ 50. Строки игрока никогда не разбираются как JSON-компонент, только `Component.literal`. Тот же санитайзер обязателен для запасного пути через наковальню.
5. **`NameSelection`** (SEC-06): выборка существует, `owner == sender`, имени ещё нет (переименовать может только оператор командой). На отказ клиент получает ключ причины без эха строки. Успех пишется в аудит-лог (SEC-47).
6. Если пакет ссылается на позицию или меню (SEC-05): меню открыто у отправителя (`containerId`, `stillValid`), позиция загружена (без загрузки чанка) и в радиусе 8 блоков, BE ожидаемого типа и не удалена, игрок не спектатор и жив. `clickMenuButton` — `id` из allowlist меню, действие идемпотентно.
7. **Ограничение частоты** (SEC-02): token bucket на (игрок, тип) с ёмкостью 5 и пополнением 5/с; `NameSelection` дополнительно ≤ 3 в минуту; кнопки меню ≤ 10/с. ≥ 200 отброшенных пакетов за 10 с → отключение (порог в SERVER-конфиге, 0 = выключено). В лог — ≤ 1 строки на игрока в 60 с.
8. Jade/WTHIT-провайдер: проверка `isLoaded` и дистанции ≤ 8, только поля тира 0, ответ ≤ 256 байт, геном не декодируется (SEC-08).
9. Исходящих соединений за пределы Minecraft нет (метрика 7). Сетевой код ограничен этим каналом; в `mods.toml` нет `updateJSONURL`. Запреты (`java.net`, `ProcessBuilder`, `URLClassLoader` и др.) проверяет ArchUnit, поведение — offline-GameTest (§17, SEC-43, SEC-44).

## 15. Клиент и сервер

- Всё под `client/` помечено `@OnlyIn(Dist.CLIENT)` там, где это ванильная практика. Подписки — `@Mod.EventBusSubscriber(modid = "wildroots", value = Dist.CLIENT)`.
- Пакеты S→C: обработчик в общем классе пакета вызывает `DistExecutor.unsafeRunWhenOn(Dist.CLIENT, () -> () -> ClientPacketHandlers.handle(msg))`. Ссылка на клиентский класс есть только внутри лямбды.
- Тултипы предметов (`appendHoverText`) вызываются и на сервере (например, в поиске JEI на интегрированном). Они не трогают `Minecraft.getInstance()`: клавиша Shift для строк тиров проверяется через `Screen.hasShiftDown()` только внутри `DistExecutor`, или через `TooltipFlag`.
- `BlockColor`/`ItemColor`, `ClientTooltipComponent` мешочка, экраны и модели регистрируются в событиях мод-шины клиента (`RegisterColorHandlersEvent`, `RegisterClientTooltipComponentFactoriesEvent`, `RegisterMenuScreensEvent`/`MenuScreens.register` в `FMLClientSetupEvent`).
- **Клиентский «пакет» мода** (что лежит под `client/` и в `assets/`): модели, blockstates, текстуры, lang (ru_ru, en_us), экраны (журнал, анализатор, лаборатория, семенной банк), тултип-компонент мешочка, цвета архетипных блоков, кэш `DefinitionsSnapshot` клиента, обработчики пакетов S→C, клиентская часть Jade/JEI-плагинов. Генетики и правил на клиенте нет.
- **Проверка:** (1) GameTest-сервер в CI — это выделенный сервер, загрузка клиентского класса из общего кода сразу его роняет; (2) архитектурный тест (§17): ни один класс вне `..client..` и вне аннотированных клиентских плагинов не ссылается на `net.minecraft.client`.

## 16. Политика mixin

Решение: ADR-0014. Порядок выбора: событие Forge → переопределение метода в своём подклассе ванильного класса → `IForge*`-расширение → access transformer → mixin. Mixin допускается, только если ничего из списка выше не работает. Каждый класс mixin — это одна цель и одна инъекция (M1 — четыре класса mixin, по одной инъекции в каждом, ADR-0014). Предпочтительны `@Inject` и `@ModifyArg`; `@Redirect` — только с обоснованием в ADR-0014 (два `@Redirect` разных модов на один вызов дают краш); `@Overwrite` запрещён. В `wildroots.mixins.json`: `"required": true`, `injectors.defaultRequire = 1`, `minVersion = "0.8.5"`, только классы из закрытого списка (CI сверяет с allowlist). Mixin в классы других модов не делаем. Обработчики — O(1), без I/O, с изоляцией исключений (`Guarded.run`, SEC-34). **Флаг отключения mixin проверяется в обработчике во время выполнения**: конфиги Forge загружаются после применения mixin, поэтому при выключенном флаге обработчик сразу возвращает ванильное поведение (SEC-45). На каждый mixin — GameTest, в том числе «флаг выключен → ваниль».

**Где лежат GameTest (WR-011):** отдельный source set `mod/src/gametest` (классы в `io.github.slugblue.wildroots.gametest`, шаблоны — `data/wildroots/structures/gametest/*.nbt`). Он подключён ко всем dev-запускам и к `runGameTestServer` как часть мода `wildroots`, но в jar не попадает. `@PrefixGameTestTemplate(false)`: id шаблона — `wildroots:gametest/<имя>`. `runGameTestServer` завершается с кодом, равным числу упавших обязательных тестов.

**Особенности GameTest-сервера 1.20.1** (выяснены в spike):
- Шаблон ставится на одну клетку выше относительного нуля `GameTestHelper`: пол шаблона лежит на относительном `y = 1`. Сущности и блоки над полом ставятся на `y = 2`, иначе сущность задыхается в полу (S2, S4).
- Игроков нет, поэтому случайных тиков нет (`ServerChunkCache.tickChunks` тикает чанки только рядом с игроком). Тесты роста вызывают `randomTick` напрямую или выставляют стадию (S3).
- Цикл дня включён: `GameTestServer` выключает только `doMobSpawning` и `doWeatherCycle`. Сервер тикает без ограничения 20 TPS: 3 игровых дня с 10 пчёлами — около 2 минут, поэтому многодневные GameTest в CI дешёвые (S2, S3).
- `GameTestServer.create` не читает `level.dat` и всегда выбирает все доступные датапаки. «Существующий мир» проверяется вызовом `ServerPacksSource.createPackRepository` + `MinecraftServer.configurePackRepository` со старым `DataPackConfig` (S1).
- Рождение ребёнка жителей в стандартной площадке не происходит и у ванильного контроля (`takeVacantBed`): тест размножения строится на площадке, где ванильный контроль рождает ребёнка, и держит этот контроль в тесте (S4).
- Рефлексия запрещена и в `src/gametest` (одно правило SEC-43 на все source set'ы): закрытые ванильные методы проверяются через публичные следствия (например, `coldEnoughToSnow`) и формулу (S11).

Forge 47.x сам принимает EULA только для GameTest-сервера (`Eula`: `ForgeGameTestHooks.isGametestServer()`), поэтому `eula.txt` в CI не нужен.

Дополнительно из threat model: фаззинг декодеров пакетов и NBT (100 000 мутированных входов на декодер, ни одного неперехваченного исключения; SEC-03, SEC-10); `MenuFuzz` — инвариант сохранения предметов во всех наших меню и в мешочке (SEC-14, SEC-17); бюджет пакетов на худших мешочках (SEC-12); ArchUnit-правила `NoNetworkNoExecTest`, `LoadedLevelAccess`, `ServerPacketGuard`, `WorldSecret` (SEC-01, SEC-25, SEC-32, SEC-43).

## 18. Зависимости и версии

Принцип: только перечисленное ниже. Новая зависимость — через ADR **и** через PR, который меняет `verification-metadata.xml` с указанием источника. Версии фиксируются точно (без `+`, диапазонов, `latest.*` и `-SNAPSHOT`; диапазоны допустимы только в `mods.toml` для рантайма игрока) в `gradle.properties` в фазе 4 (SEC-38). Репозитории — только официальные, по https, каждый через `exclusiveContent` со своим набором групп (SEC-37): `maven.minecraftforge.net`, `maven.parchmentmc.org`, `repo.spongepowered.org`, Gradle Plugin Portal (только плагины), Maven Central, `maven.blamejared.com` (только `mezz.jei`), `maven.terraformersmc.com` (только `dev.emi`), `api.modrinth.com/maven` (только `maven.modrinth`: FD, Jade). `mavenLocal`, JitPack, `flatDir` и `http://` запрещены. CurseMaven — только если зависимости нет на Modrinth Maven. Координаты WTHIT — `[ПРОВЕРИТЬ]`. **Как сделано в фазе 4 (WR-008):** в `pluginManagement` Forge, Parchment, SpongePowered и Plugin Portal (только `org.gradle.toolchains*`) объявлены через `exclusiveContent`, а Maven Central — общий запасной репозиторий для обычных библиотек classpath плагинов (gson, asm и т. п.): их группы заранее не перечислить. ForgeGradle 6 сам добавляет в проект `:mod` свои репозитории (Forge, Mojang libraries, Maven Central, локальные кэши), поэтому `repositoriesMode = FAIL_ON_PROJECT_REPOS` и `PREFER_SETTINGS` неприменимы; наши репозитории проекта объявлены в `build.gradle` через `exclusiveContent`. Подмену артефакта из любого репозитория ловит `verification-metadata.xml` (SEC-40). Скрипт `ci/check-repositories.sh` запрещает `mavenLocal`, JitPack, `flatDir`, `http://` и хосты вне списка. Где я не уверен в номере, стоит `[ПРОВЕРИТЬ]`: фаза 4 сверяет номер с файлами Maven и MDK и заменяет пометку конкретным числом.

## 19. Ответы на вопросы из STATUS.md

| Вопрос | Ответ | Где |
|---|---|---|
| **`village_farmland` (П16)** | Флаг на пашне не нужен. Деревенская клетка — это наше растение с `village = true` или блок-жнивьё `wildroots:village_plot`. Их ставит только генерация деревни. Фермер собирает только их (через `getAge`, от которого считается `final`-метод `isMaxAge`; S3) и в том же тике пересаживает шаблоном. Пашня игрока деревенской не становится, кран ограничен исходным полем | §11.6, ADR-0010 |
| **`forge:conditions` / `line_loaded` в 47.x** | S1: в рецептах ключ `"conditions"`, в datapack-реестрах (biome modifier, placed feature) — `"forge:conditions"`; своё условие через `CraftingHelper.register` работает в обоих. Основной путь всё равно — встроенные обязательные пакеты линий (`AddPackFindersEvent`), JSON в них без условий; условия — вторичный механизм. `line_loaded` остаётся для рецептов и достижений ядра | §9, ADR-0006 |
| **AI жителей для геномных культур** | `FieldPlantBlock extends CropBlock` + `getAge = max` только при `village && зрелость` (`isMaxAge` — `final`, S3); урожай в инвентарь жителя в `getDrops`, пересадка — очередью в конце тика уровня; mixin только для еды жителей (M1) | §11.6, ADR-0010 |
| **Хук классов в рецептах FD** | Разделочная доска — данными (`partial_nbt` + `difference`). Котёл по умолчанию без класса (запасной путь, дефолт владельца). Подкласс `CookingPotRecipe` за флагом, если spike S6 покажет `assemble` | §12.2, ADR-0012 |
| **Id блоков из нарратива** | `gourd_fruit`, `watermelon_fruit`, `apple_trunk`, `apple_leaves`, `apple_fruit` — **принимаются** как id блоков (+ нужен `apple_log` для верхних блоков ствола). `cacao_pod` **не нужен** отдельным блоком: растение какао и есть стручок на стволе, его блок — `wild_cacao` (один блок на вид). Строку «Стручок какао» можно оставить как имя стадии. Архетипные блоки датапачных видов: `generic_field_plant`, `generic_tall_plant`, `generic_water_plant`, `generic_vine`, `generic_vine_fruit`, `generic_bush`; плюс `village_plot` | §7.1 |
| **Ввод имени сорта яблони** | Основной путь — поле в экране журнала (свой экран всё равно нужен) → пакет `NameSelection` с проверками (§14). Имя хранится в `SavedData` `named_selections` и задаётся один раз. Запасной путь — переименование привоя на наковальне: при первой прививке или посадке клона сервер переносит имя в выборку, как `line_name` у лота | §6.1, §14 |
| **Jigsaw ≤ 1 хижины** | Вариант Б: хижина как вариант стартового элемента деревни — ровно один на деревню по построению, частота задаётся весом точно. Запасной вариант — свой тип элемента + mixin M6 | §11.7, ADR-0011 |
| `pile_pumpkin`/`pile_melon` (worldgen §15.2 №4) | Плод-блоки ландраса; нагрузка ничтожная | §11.5 |
| Малина на `coarse_dirt` (worldgen §15.2 №3) | Фермер её не трогает; куст многолетний, пересадка не нужна | §11.6 |
| Подстановка BE-блока в ванильную `tree`-feature (worldgen §3.6) | В `trunk_provider` можно указать наш блок, но BlockEntity с паспортом ванильный `TreeFeature` не заполнит `[ПРОВЕРИТЬ]` → своя feature дерева в `worldgen` | §3 (пакет `worldgen`) |

## 21. Отклонения от спецификации и вопросы к владельцу

Уточнения, которые вынуждены реализацией (игровое ощущение не меняется, если не сказано иное):

1. **Ключ RNG потомка** — `hash(secret, lotId, оставшееся число, позиция)` вместо `hash(lot_id, seed_index)` (GDD §3.8). Позиция нужна, иначе две половинки разделённого стака давали бы одинаковых потомков. Секрет мира (SEC-25) не даёт модифицированному клиенту вычислить потомка заранее. Перезаход по-прежнему ничего не перебрасывает. Что падает с молодого растения, если его сломать (против reroll, SEC-26), решает Game Designer; архитектура требует только, чтобы повторная посадка не давала нового броска.
2. **Окраска урожая не хранится в предмете** (иначе не уложиться в 6 вариантов). Она видна на растении и в тултипе лота. `[Game Designer]` подтвердить.
3. **Датапачный вид** (метрика 6) получает архетипный блок с окрашенной общей моделью и общий предмет урожая без Forge-тегов. Деревья, тростник и какао-подобные — только встроенные. `[Владелец]` подтвердить объём.
4. **Хижина селекционера — вариант стартового элемента деревни**, а не дом в пуле домов (worldgen §11.5). `[Level Designer]` принять; иначе mixin M6.
5. **FD-блюда без класса в MVP** (дефолт владельца «да»). Хук котла — за флагом после spike S6.
6. **Геном лота виден модифицированному клиенту** (ванильная синхронизация предметов); честный клиент показывает только то, что разрешают флаги знания. С секретом мира Security оценивает риск как Low (`09-security.md` §1.8, вариант А). `[Владелец]` принять или выбрать шифрование генома ключом мира (вариант В, предметы привязываются к миру).
7. **Пчёлы выбирают наши растения через индекс цветения** (не сканирование, но и не ванильный поиск цветов). `[Game Designer]` подтвердить трактовку GDD §13.
8. **Глобальная зачистка шаблонов структур отложена** (нужен mixin); ванильные культуры в чужих структурах убираются случайным тиком и GLM.
9. **Торт и блок арбуза без класса** (economy П26).
10. **`disabledLines` — COMMON-конфиг, смена требует перезапуска.**
11. **Мешочек нельзя положить в шалкер или bundle** (отличие от ванильного bundle) и **семенной банк роняет содержимое** при разрушении. Это дефолт из threat model (SEC-11); `[Владелец]` подтвердить.
12. **Следствие SEC-23 для модовых деревень.** Страховочная сеть worldgen §11.4 становится уже: в чанках, сгенерированных **после** включения линии (маркер `wr_lines`), ванильные культуры модовых деревень с собственными процессорами ферм превращаются в **дикие** растения, а не в живой ландрас, и фермеры там не работают. Я принимаю это как цену защиты деревенского фонда от подделки: кровать и компостер игрока не должны делать грядку деревенской. Ванильные деревни не затронуты (их обслуживает процессор). `[Level Designer]` знать.
13. **Окно свежести пыльцы пчелы** (GDD §4.3: ≤ 1200 тиков) считается в тиках жизни пчелы **вне улья**: по мировому времени окно недостижимо из-за ванильного цикла улья (S2, §10.3). `[Game Designer]` подтвердить; после ответа правится GDD §4.3. Вопрос — в `STATUS.md`.
14. **Книга рецептов не раскладывает урожай с классом** (ванильное `isSameItemSameTags`, S5, §12.1): игрок кладёт его в сетку вручную. `[Narrative Designer]` — подсказка в журнале.
15. **Перекрытие ванильного рецепта линией проигрывает моду, установленному после появления линии в мире** (S1, §9.2). Принято как известная несовместимость; `[Владелец]` подтвердить.
16. **Фермер с ванильными семенами в инвентаре** сажает их на любую пустую пашню рядом с собой, в том числе на пашню игрока (ванильное поведение, S3, §11.6 п. 3). Дефолт — не менять тег `#minecraft:villager_plantable_seeds`; `[Владелец]`/`[Economy Designer]` подтвердить.

**Правки из threat model (`09-security.md` §1.9, Δ1–Δ9) внесены полностью.** Несогласий по существу нет. Два уточнения:
- **SEC-45, флаг отключения mixin:** выбрана только проверка в обработчике во время выполнения. Вариант с `IMixinConfigPlugin.shouldApplyMixin`, который сам читает файл COMMON-конфига, не берём: второй разборщик конфига вне `ForgeConfigSpec` дублирует логику и может разойтись с ним. Цена — инъекция всё равно применяется, и при конфликте `require = 1` с чужим `@Overwrite` краш при старте остаётся. Это остаточный риск из `09-security.md` §1.10.
- **SEC-19, механизм сделок:** если S13 не подтвердит подкласс или событие, я рекомендую меню услуг на сортировочном столе, а не M7 (совпадает с рекомендацией Security, вопрос 6 владельцу).
